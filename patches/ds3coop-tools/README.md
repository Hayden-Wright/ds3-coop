# Инструменты диагностики — что это и как проверить

Дата: 2026-10-24.

## Зачем это нужно

Прежде чем менять игру, нужно ответить на вопрос: **как игра понимает, что игрок — гость.**
Без этого любой патч будет гаданием.

Эти инструменты ничего не меняют в игре. Они только:
- запускают игру так же, как лаунчер мода;
- читают служебную информацию из памяти игры;
- пишут текстовый лог.

**Игру они не патчат, байты не меняют, античит не трогают.**

## Состав

| Файл | Что делает |
|---|---|
| `src/ds3coop_launcher.cpp` | Свой лаунчер. Запускает `DarkSoulsIII.exe` и внедряет DLL — как это делает `ds3sc_launcher.exe` от автора мода, но умеет грузить сразу несколько DLL. |
| `src/ds3coop_tools.cpp` | Диагностическая DLL. Проверяет версию игры и ищет в памяти объекты меню. Пишет лог. |

## Почему свой лаунчер, а не родной

Родной `ds3sc_launcher.exe` грузит ровно один файл — `SeamlessCoop\ds3sc.dll`.
Наш грузит его же плюс наш диагностический слой. Файлы автора при этом
**не изменяются**: мы только запускаем игру другим способом.

## Проверка идентичности игры

DLL сверяет два значения из заголовка `DarkSoulsIII.exe`:

| Параметр | Ожидание |
|---|---|
| Размер образа | `0x56f4000` |
| Timestamp | `0x639c4ddd` |

Оба значения взяты из открытого проекта The Ashen Link, где они используются
как проверка совместимости. Для нашей установки они **совпали** (проверено
отдельно, см. `notes/02-what-works.md`).

Если значения не совпадут, в логе будет `ИТОГ: FAIL (версия игры)` — значит,
игра обновилась и адреса из чужих наработок применять нельзя.

## Как проверить (можно делать сегодня, без друга)

1. Скопировать в папку игры `Game\`:
   - `ds3coop_launcher.exe`
   - `SeamlessCoop\ds3coop_tools.dll`
2. Запустить `ds3coop_launcher.exe`.
3. Игра должна открыться как обычно.
4. Закрыть игру.
5. Открыть файл `Game\SeamlessCoop\ds3coop-tools.log`.

**Что должно быть в логе:**

```
ds3coop-tools: загрузка
база игры      : 0x...
размер образа  : 0x56f4000 (ожидался 0x56f4000)
timestamp      : 0x639c4ddd (ожидался 0x639c4ddd)
идентичность   : СОВПАЛА
строка SprjMenuMan найдена по адресу 0x...
ИТОГ: PASS
```

`ИТОГ: PASS` — инструмент работает, можно двигаться дальше.
`ИТОГ: FAIL` — присылайте лог, разберёмся.

## Что это доказывает

- Мы умеем запускать игру с несколькими DLL одновременно.
- Мы умеем читать память игры безопасно (с проверкой доступности страниц).
- Мы умеем находить объекты игры по имени класса, не зная жёстких адресов.

Это фундамент для патча. Сам патч (разрешить гостю меню) — следующий шаг,
и он требует второго игрока для проверки.

## Сборка

```bash
cd patches/ds3coop-tools
x86_64-w64-mingw32-g++ -std=c++20 -O2 -shared -static \
  -static-libgcc -static-libstdc++ \
  -o build/ds3coop_tools.dll src/ds3coop_tools.cpp

x86_64-w64-mingw32-g++ -std=c++20 -O2 -municode \
  -o build/ds3coop_launcher.exe src/ds3coop_launcher.cpp \
  -static -static-libgcc -static-libstdc++
```

Проверено: компилятор `x86_64-w64-mingw32-g++ 13-posix`, сборка проходит без ошибок,
на выходе PE32+ x86-64.

**Флаг `-static` обязателен.** Без него DLL линкуется с `libwinpthread-1.dll`,
которого на обычной Windows нет, и загрузка падает с ошибкой 126
(`ERROR_MOD_NOT_FOUND`). Это поймано тестом: DLL молча не грузилась,
и лог не создавался.

После сборки зависимости должны быть только системные:

```bash
objdump -p build/ds3coop_tools.dll | grep "DLL Name"
# должно быть только KERNEL32.dll и msvcrt.dll
```

## Исправление 2026-10-24 (ночь), версия сборки 01:28

**Найдено два дефекта, оба исправлены до запуска в игре.**

### Дефект 1: работа внутри `DllMain`

Вся диагностика выполнялась прямо в `DllMain`. Там Windows держит блокировку
загрузчика: пока код не вернётся, процесс не может грузить другие модули.
Долгий скан внутри `DllMain` подвешивает старт игры.

**Исправлено:** в `DllMain` осталось только открытие лога и `CreateThread`.
Вся работа — в отдельной функции `Worker`.

### Дефект 2: `VirtualQuery` на каждый байт

Поиск строки шёл побайтово по образу игры (87 МБ), и на каждой позиции
вызывался `VirtualQuery`. Это 87 миллионов системных вызовов.

**Замер** (Windows, `QueryPerformanceCounter`, 1 000 000 вызовов):
`0.821 мкс` на вызов → **≈71 секунда** на один проход.

**Исправлено:** обход памяти регионами, один `VirtualQuery` на регион.
Скорость самого поиска замерена на буфере 256 МБ: **966 МБ/с**,
то есть образ игры 87 МБ проходится примерно за **90 мс**.

### Что проверено после исправления

- Сборка без предупреждений (`-Wall -Wextra`), зависимости только системные.
- Загрузка DLL в служебный процесс Windows: `LoadLibrary` успешна, лог создаётся.
- Отсутствие игры обрабатывается корректно: `ИТОГ: FAIL (игра не загрузилась)`.
- В лог добавлены замеры времени (`поиск строки`, `поиск ссылки`, `всего`),
  чтобы при первом запуске видеть реальную стоимость на настоящей игре.

**Не проверено:** запуск с настоящей игрой. Нужен запуск владельцем.

## Исправление 2026-10-24 (ночь), версия сборки лаунчера 01:43

**Повод:** первый запуск владельцем не дал лога. Проверено по времени:
игра стартовала 01:36:34, мод загрузился (обновился `crashdumps\settings.dat`),
сейв записан 01:37:54, приложение закрыто 01:38:07. Нашей DLL в процессе не было.
Владелец подтвердил: запускал **`ds3sc_launcher.exe`** — родной лаунчер мода.

Это не дефект, а ожидаемое поведение: родной лаунчер грузит только `ds3sc.dll`.
Но отличить запуски задним числом было нечем, поэтому добавлен лог лаунчера.

**Что добавлено в лаунчер:**
- Пишет `SeamlessCoop\ds3coop-launcher.log` при каждом запуске: время, каталог,
  наличие файлов, PID игры, результат внедрения каждой DLL.
- Если этого файла нет — игру запускали не нашим лаунчером. Это и есть признак.
- В логе есть `ИТОГ: лаунчер отработал` или `ИТОГ: FAIL (...)`.

**Найденные и исправленные дефекты по ходу:**
1. `%s` во `vfwprintf` из mingw означает `char*`, а не `wchar_t*` — путь в логе
   обрезался до `D`. Исправлено на `%ls`.
2. Кириллица в консоли превращалась в мусор: `fwprintf` конвертирует через
   C-locale. Заменено на `WriteConsoleW`; при перенаправленном stdout —
   запасной путь через UTF-8.
3. Приведение `FARPROC` к `LPTHREAD_START_ROUTINE` давало предупреждение —
   исправлено приведением через `void*`. Сборка чистая, `-Wall -Wextra`.

**Проверено на фальшивой «игре»** (маленький exe, который просто живёт 6 секунд):
лаунчер внедрил обе DLL, диагностика отработала в отдельном потоке, определила
несовпадение версии и написала `ИТОГ: FAIL (версия игры)`. Весь конвейер цел.

**Установлено в игру:** `ds3coop_launcher.exe` SHA-256 `a9403a7a…`.

## Исправление 2026-10-24 (ночь), версия сборки DLL 01:49

**Повод:** первый успешный запуск нашим лаунчером дал лог, и в нём обнаружилось
противоречие — числа совпадают, а вердикт «НЕ СОВПАЛА».

```
размер образа  : 0x56f4000 (ожидался 0x56f4000)
timestamp      : 0x639c4ddd (ожидался 0x0639c4dd)   <-- вот здесь
идентичность   : НЕ СОВПАЛА
```

**Дефект 1 — опечатка в константе.** В коде стояло `0x639c4ddu`, это
`0x0639C4DD` — на одну hex-цифру меньше. В файле игры `0x639C4DDD`
(проверено байтами заголовка: `dd 4d 9c 63`). Из-за этого проверка версии
не могла пройти никогда. Исправлено на `0x639c4dddu`.

**Дефект 2 — строка `SprjMenuMan` в игре отсутствует.** Она была взята из
`ds3sc.dll` (мод) — там она есть, в `DarkSoulsIII.exe` её нет вообще
(проверено: 0 вхождений в файле игры). Настоящее RTTI-имя класса —
`NS_SPRJ::MenuMan`, строка `.?AVMenuMan@NS_SPRJ@@`, RVA `0x4588310`.
Заменено.

**Как проверено без запуска игры** (отдельная утилита читает exe с диска):

```
timestamp в файле : 0x639c4ddd, константа: 0x639c4ddd -> СОВПАЛО
SizeOfImage в файле: 0x56f4000, константа: 0x56f4000 -> СОВПАЛО
строка ".?AVMenuMan@NS_SPRJ@@": вхождений 1, offset 0x4588310
старое имя "SprjMenuMan": вхождений 0 (ожидалось 0)
ИТОГ ПРОВЕРКИ: PASS
```

**Дополнительно:** при несовпадении версии лог теперь печатает конкретную
причину (`размер образа не совпал` / `timestamp не совпал`), а при найденной
строке — её RVA. Раньше разбор лога превращался в угадывание.

**Проверено:** сборка чистая (`-Wall -Wextra`), зависимости только системные;
загрузка в служебный процесс с новыми константами корректна — фальшивая игра
даёт `ИТОГ: FAIL` и обе причины.

**Установлено в игру:** `ds3coop_tools.dll` SHA-256 `7ad51a9e…`.

## Версия 2 — поиск живых объектов игры (2026-10-24, 02:11)

**Что нового.** Раньше DLL только проверяла версию и искала строку. Теперь она
находит **живые объекты игры в памяти** — и это основа для патча.

**Как это работает.** У объекта C++ первое поле — указатель на его таблицу
виртуальных функций (vtable). Значит, живой объект класса ищется так: пройти
доступную память процесса и найти слова, равные `база_игры + RVA vtable`.
Абсолютных адресов нет — всё считается от базы, поэтому ASLR не мешает.

**Откуда взялись RVA vtable.** Разобрана RTTI игры (см. `notes/04-offsets.md`
в корне проекта): строка имени → `TypeDescriptor` → `CompleteObjectLocator` →
`vftable[-1]`. Получены адреса для 10 классов: `MenuMan`, `FrpgMenuSys`,
`InGameMenuStep`, `CsPlayerMenuCtrl`, `FrpgMenuDlgShopExtList`,
`FrpgMenuDlgWarp`, `MenuData`, `PlayerIns`, `ChrIns`, `GameMan`.

**Каждое значение проверено** тремя условиями: сигнатура COL, указатель на
дескриптор типа, обратный указатель из vtable, совпадение имени. Все 10 прошли.

**Что пишет в лог:** сколько объектов каждого класса найдено, их адреса и
первые 8 слов. Поиск повторяется 6 раз с интервалом 5 секунд, поэтому видно,
когда игра создаёт объекты (вход в мир, открытие меню).

**Защита от чужой версии.** Если версия игры не совпала, поиск **пропускается**:
на другой версии эти RVA указывают в случайные места, и «найденные объекты»
были бы мусором.

**Исправленный дефект:** в `DumpObject` было переполнение буфера — `snprintf`
возвращает длину, которую хотел записать, а не ту, что записала, и счётчик
уходил в минус. Поймано на заглушке: строки в логе слипались.

**Проверено:** сборка чистая, зависимости системные, на заглушке — корректный
отказ и пропуск поиска. **На живой игре не проверено.**

## Версия 2.1 — исправлено падение игры (2026-10-24, 02:40)

**Что случилось.** Первый запуск v2 уронил игру через ~2 секунды после старта
поиска объектов. Лог обрывался на середине второго прохода. Журнал Windows:

```
Faulting module name: ds3coop_tools.dll
Exception code: 0xc0000005
Fault offset: 0x00000000000019fd
```

Падала **наша** DLL, а не игра. По смещению `0x19fd` дизассемблер даёт
инструкцию `cmp (%rbx),%rbp` — это внутренний цикл поиска объектов.

**Причина.** `VirtualQuery` сообщает, что регион читаемый, но между проверкой
и чтением игра успевает освободить страницу. Прямое чтение по указателю
роняет весь процесс. Проверка и чтение не атомарны.

**Исправление.**

1. `SafeRead` — чтение через `ReadProcessMemory`. На освобождённой или
   защищённой странице возвращает `FALSE` вместо падения процесса.
2. Поиск читает память кусками по 64 КБ через `SafeRead`.
3. `DumpObject` тоже через `SafeRead` — объект мог исчезнуть между поиском
   и чтением; тогда в лог идёт `[объект уже освобождён, чтение отменено]`.
4. `FindInstances` заменена на `FindAllInstances`: **один проход по памяти
   обслуживает все 10 классов** вместо 10 отдельных проходов.

**Замеры на стендах (не на игре):**

| Проверка | Результат |
|---|---|
| Прямое чтение освобождённой страницы | процесс падает, код возврата 5 |
| `ReadProcessMemory` на той же странице | `ok=0`, процесс жив |
| Поиск: 2 объекта класса A, 1 класса B | найдены все 3 по точным адресам |
| Перекрёстные ложные срабатывания | нет |

**Сборка:** без предупреждений (`-Wall -Wextra`), зависимости только
`KERNEL32.dll` и `msvcrt.dll`. SHA-256 `08df4ac3…`.

**Статус:** установлено в игру. На живой игре ещё не проверено — нужен запуск.

## Версия 2.2 — исправлено два дефекта лога (2026-10-24, 02:55)

Запуск v2.1 в 02:31 прошёл успешно: игра не упала, лог дошёл до конца,
`ИТОГ ДИАГНОСТИКИ: PASS`, 6 проходов за 67 437 мс. Но в самом логе нашлись
две ошибки, из-за которых результаты были неверными.

### Дефект 1: поиск находил сам себя

В логе появились «объекты», идущие строго через 8 байт:

```
MenuMan @ 0x199b2666430: [00]=7ff7187080b0 [08]=7ff718706848 ...
MenuMan @ 0x199b2666438: [00]=7ff718706848 ...
```

Это не объекты игры, а **наш собственный массив `vftables` в куче**. Он
состоит ровно из тех значений, которые мы ищем, поэтому попадал в результаты.

*Исправлено:* `FindAllInstances` принимает список исключаемых диапазонов;
в него заносится собственная память диагностики.

### Дефект 2: печатался объект, успевший измениться

Строка `GameMan @ 0x91466ff388` показала `[00]=7ffeaa0172ef`, хотя первым
полем обязан быть адрес vtable. Объект освободили между поиском и печатью.

*Исправлено:* `DumpObject` перепроверяет первое поле и при несовпадении
пишет `[объект изменился … пропуск]`.

### Дефект 3 (профилактика): резервирование памяти

`push_back` без `reserve` перевыделяет буфер и освобождает старые блоки.
Следующий проход мог прочитать в них остатки прежних значений. Добавлен
`reserve(max_hits)`.

### Проверка

Стенд воспроизводит ошибку из лога: массив искомых адресов лежит в куче.
Результат — настоящий объект найден, свой массив **не** найден. Три ветки
`DumpObject` проверены отдельно:

```
Stale @ 0x243ddd10000: [объект изменился, уже не Stale — пропуск]
Freed @ 0x10: [объект уже освобождён, чтение отменено]
```

**Сборка:** без предупреждений, зависимости `KERNEL32.dll` и `msvcrt.dll`.
SHA-256 `160f2964…`. Установлено в игру.
